= Module 6: Credential security
:navtitle: Module 6: Credential security

The usual way to give an agent an API key is an environment variable, and then the agent can print,
log or send it. This module answers: *can the agent see our LLM key, and is what it holds worth
stealing?*

You will look for the key inside the sandbox, use the placeholder through the boundary, and then try
the same placeholder from outside.

.New to boundary credential resolution?
[%collapsible]
====
* *Provider* — an OpenShell record that holds a credential for one upstream service (here, MaaS).
* *Resolver token* — the placeholder `openshell:resolve:env:…` the sandbox sees in place of the key.
* *Boundary* — the supervisor's egress proxy, which swaps the placeholder for the key on allowed requests.
====

== Technical context

[cols="1,3",options="header"]
|===
| Stage | Where the key is

| Install
| The Helm value goes to Vault (`secret/hub/infra/openshell/maas`) and to the Secret `maas-api-key`
| Setup
| The setup Job registers the key with the gateway as the credential of the `maas` provider
| Runtime
| The sandbox gets only a resolver token; the supervisor attaches the key to requests bound for `{maas_host}`
|===

== Learning objectives

* Show that no form of the real key exists in the sandbox environment.
* Show the placeholder working through the boundary and failing everywhere else.

== Exercise 1: Look for the key inside the sandbox

[source,bash,role="execute",subs="attributes+"]
----
openshell sandbox exec {sandbox_name} < /dev/null -- bash -c 'env | grep -i maas; env | grep -c "sk-"'
----

Expected result: one line, `MAAS_API_KEY=openshell:resolve:env:v…_MAAS_API_KEY`, and the count `0`: no
`sk-` value anywhere in the sandbox environment.

== Exercise 2: Use the placeholder through the boundary

[source,bash,role="execute",subs="attributes+"]
----
openshell sandbox exec {sandbox_name} < /dev/null -- bash -c 'curl -s -o /dev/null -w "MaaS HTTP %\{http_code}\n" --max-time 5 https://{maas_host}/v1/models -H "Authorization: Bearer $MAAS_API_KEY"'
----

Expected result: `MaaS HTTP 200`. The request left the sandbox with the placeholder, and MaaS received the
real key.

== Exercise 3: Try the placeholder elsewhere

NOTE: Both attempts fail. This is expected: they are what an attacker who stole the placeholder would try.

First from inside the sandbox, against a different API:

[source,bash,role="execute",subs="attributes+"]
----
openshell sandbox exec {sandbox_name} < /dev/null -- bash -c 'curl -sS --max-time 5 https://api.openai.com/v1/models -H "Authorization: Bearer $MAAS_API_KEY"; echo "exit=$?"'
----

Expected result: `curl: (7) Failed to connect to api.openai.com` and `exit=7`: the placeholder never leaves
the sandbox for a host outside the allowlist.

Then copy the placeholder out of the sandbox and send it to MaaS directly from your Web Terminal, outside
the boundary:

[source,bash,role="execute",subs="attributes+"]
----
TOKEN=$(openshell sandbox exec {sandbox_name} < /dev/null -- printenv MAAS_API_KEY 2>/dev/null | grep '^openshell:resolve')
echo "stolen: ${TOKEN:0:30}..."
curl -s -w "\nHTTP %\{http_code}\n" --max-time 10 https://{maas_host}/v1/models -H "Authorization: Bearer $TOKEN" | tail -c 160
----

Expected result: `stolen: openshell:resolve:env:v…`, then an `auth_error` saying a key `expected to start
with 'sk-'` and `HTTP 401`. The same string that got `HTTP 200` in Exercise 2 is worthless here.

In short: the agent can use the key only for the one service it is bound to, and only from inside the sandbox.

== Evidence checkpoint

* Who could still read the real key on this cluster, and why is that acceptable?
* What would an attacker need, besides the placeholder, to use the key?

.Answer key
[%collapsible]
====
* Cluster administrators, from Vault or the Secret `maas-api-key` (Module 7 reads its first characters).
  The boundary protects the key from the agent, not from the platform's administrators.
* Code running inside this sandbox, calling the MaaS host through the supervisor; the placeholder alone does nothing.
====
