Run an autonomous AI coding agent on OpenShift, then prove what it cannot do.

AI coding agents such as link:https://pi.dev/[Pi^] write code, install packages, call APIs and run
programs on their own. An unconstrained agent can therefore send your source code to any server,
read any file in its container, and leak the LLM API key it was given. This lab runs the Pi agent
inside an NVIDIA OpenShell sandbox on a cluster that already runs the Red Hat Zero Trust Validated
Pattern (ZTVP), and asks you to verify each restriction yourself instead of taking it on trust.

The lab progresses through these tasks:

. Register OpenShell's Helm chart in the Developer Catalog and install it, with its API key in Vault and no public endpoint.
. Connect the OpenShell CLI to the gateway.
. Watch Pi write and run code through the Red Hat MaaS LLM.
. Prove that the sandbox reaches only three approved hosts.
. Prove that the Linux kernel (Landlock) limits which paths the agent can write.
. Prove that the real API key never enters the sandbox.
. Trace how Vault, External Secrets, SPIRE, ACS and Keycloak plug into OpenShell.
. Obtain a Keycloak token for the gateway's OIDC client.
. Change the network policy of a running sandbox, then revoke the change.

== Learning objectives

By the end of the lab you will be able to:

* Deploy OpenShell on OpenShift from a Helm chart repository registered in the Developer Catalog, reachable only from inside the cluster.
* Demonstrate allowed and denied egress from an agent sandbox, and explain why denial is immediate.
* Demonstrate Landlock filesystem enforcement inside a container, including for paths a root user would normally write.
* Explain how a resolver token keeps the real LLM credential outside the sandbox.
* Locate the Vault path, ExternalSecret, ClusterSPIFFEID and Keycloak client that the chart wires up.
* Update a sandbox network policy live and verify the change, then revert it.

== How to run the lab

Each exercise names the state to change, the evidence to inspect, and the
result that must be verified. Do not treat command completion as proof.
Compare the observed resource, policy, or event with the stated expected
result before continuing. Facilitators: see
xref:92-facilitator-guide.adoc[Facilitator Guide].

Every module, and the Web Terminal setup, includes a short video recorded on a lab cluster during a full run of
this guide. A banner names each exercise, yellow boxes mark the output that proves the result, and waits for a
command to finish are sped up (marked *sped up*). Watch a video to see a step before you run it, or to compare when
your own output differs. LLM output (Module 3) and generated names and timestamps will differ from yours.

== Technical model

* *OpenShift* runs every component and provides the Developer Catalog, Routes and the Web Terminal.
* *ZTVP* provides the shared security services: Vault (secrets), External Secrets Operator (secret sync),
  Keycloak (user identity), SPIFFE/SPIRE (workload identity) and Advanced Cluster Security (image and runtime policy).
* *OpenShell* adds the gateway, a supervisor that sits between the agent and the network, and the policy engine.
* *Landlock*, a Linux kernel security module, enforces the sandbox filesystem policy.
* *Pi* is the agent under test, and *Red Hat MaaS* (Model-as-a-Service) is the LLM it calls.

No single layer is enough on its own. Kubernetes NetworkPolicy works per pod, not per process. Vault keeps a
secret encrypted but hands it to whoever may read it. A container filesystem limits nothing for root.
OpenShell's per-binary egress rules, Landlock, and boundary-side credential resolution close those gaps, and
ZTVP supplies the identities and secrets that OpenShell consumes.
