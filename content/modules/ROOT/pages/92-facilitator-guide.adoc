= Facilitator Guide
:navtitle: Facilitator Guide

For facilitators provisioning lab environments ahead of class. Participants can skip this page.

Each participant gets a dedicated cluster. The lab was verified on single-node OpenShift {ocp_version}
on AWS (`m6i.8xlarge`, 32 vCPU and 128 GiB, 300 GB gp3) running the full Zero Trust Validated Pattern.

== Provision on RHDP

The repository root is a Red Hat Demo Platform field-content chart. Order the *Field Content CI* on a cluster
with at least 32 vCPU and 128 GiB (the lab was verified on single-node `m6i.8xlarge`), and set:

[cols="1,2",options="header"]
|===
| Order field | Value

| Existing Gitops Repo?
| checked
| GitOps Repo
| `https://github.com/hultzj/openshell-lab`
| GitOps Revision
| the branch to deploy (`field-automation`)
| GitOps Path
| `.` (the chart is at the repository root)
|===

IMPORTANT: Type `.` in *GitOps Path*; do not leave it empty. The workload renders an empty path as `path:` with no
value, and Argo CD rejects such an Application with `InvalidSpecError: spec.source.repoURL and either spec.source.path
or spec.source.chart are required` (observed with OpenShift GitOps 1.22). The chart treats `.` and an empty path the
same, so it is ready for a workload fix.

The order creates one Argo CD Application, `field-content`, in `openshift-gitops`. It deploys three children:

[cols="1,3",options="header"]
|===
| Application | What it does

| `field-content-ztvp`
| Installs the patterns operator and the `layered-zero-trust` Pattern, then the Job `ztvp-load-secrets` runs the
  pattern's own `load-secrets` playbook in the cluster once Vault and External Secrets are up. ZTVP takes 30 to 40
  minutes after the order completes.
| `field-content-prereqs`
| Subscribes the Web Terminal operator, and the Job `participant-setup` creates `{lab_user}` (identity provider
  `openshell-lab-htpasswd`, cluster-admin) with a random password. Raises the node's pod limit from 250 to 500
  (`prereqs.maxPods`): a single-node order with OpenShift AI and the pattern runs about 260 pods, and past the limit
  the participant's Web Terminal cannot start. The change reboots the node once, during provisioning.
| `field-content-showroom`
| Deploys this guide from the same repository and revision, with the RHDP Showroom chart vendored in
  `components/showroom`. Its newer git-cloner fails and retries when DNS is not up after a node reboot; the
  upstream one reported success with an empty checkout, and the guide stayed in `Init:Error`.
|===

The order page shows the cluster's own access details (console, `admin` login, MaaS key) but not the lab's: the
field-content workload creates the Application and exits without reading the lab's `demo.redhat.com/userinfo`
ConfigMaps. Read the `{lab_user}` password from the cluster once `participant-setup` has run, logged in as the
order's `admin` user:

[source,bash]
----
oc get secret lab-user-credentials -n openshell-lab -o jsonpath='{.data.password}' | base64 -d; echo
----

The OAuth server then rolls out the new identity provider, so the first login works about two minutes after the Job
completes. On the console login page, choose `openshell-lab-htpasswd`; the other provider is the order's own Keycloak.

The RHDP base install already runs cert-manager (it issues the cluster's public ingress certificate) and the Red Hat
build of Keycloak 26.6 (cluster login). The chart's `ztvp.extraParameters` make the pattern reuse cert-manager's
OperatorGroup and follow Keycloak 26.6. Without them OLM fails cert-manager for the whole cluster (two OperatorGroups
in one namespace) and refuses the pattern's Keycloak 26.4, and the pattern never installs Vault. If an order shows
`InstallPlanFailed` on `rhbk-operator` in `keycloak-system`, compare its channel with
`oc get subscription -n keycloak -o jsonpath='{.items[*].spec.channel}'`.

The chart assumes the order's Argo CD controller is cluster-admin, as the field-content examples need. `make
-C automation verify` checks it.

== Provision any other cluster

The same chart, applied by `make -C automation bootstrap`. The cluster needs OpenShift GitOps first; a cluster that
already runs ZTVP has it. Otherwise install it the way RHDP does (channel `latest`, default instance in
`openshift-gitops`) and give its controller cluster-admin, as the chart creates operators and ClusterRoleBindings:

[source,bash]
----
oc apply -f - <<'EOF'
apiVersion: v1
kind: Namespace
metadata: { name: openshift-gitops-operator }
---
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata: { name: openshift-gitops-operator, namespace: openshift-gitops-operator }
spec: { upgradeStrategy: Default }
---
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata: { name: openshift-gitops-operator, namespace: openshift-gitops-operator }
spec: { name: openshift-gitops-operator, channel: latest, source: redhat-operators, sourceNamespace: openshift-marketplace }
EOF
until oc get argocd openshift-gitops -n openshift-gitops >/dev/null 2>&1; do sleep 10; done
oc adm policy add-cluster-role-to-user cluster-admin -z openshift-gitops-argocd-application-controller -n openshift-gitops
----

Then use `ZTVP=true` on a cluster without the pattern, or `ZTVP=false` (the default) on one that already runs it:

[source,bash]
----
make -C automation bootstrap ZTVP=true
make -C automation status
----

The Applications go to the Argo CD instance in `openshift-gitops` if the cluster has one, otherwise to `vp-gitops`
(ZTVP's own); set `GITOPS_NS` to override. Repeat `status` until every Application shows `Synced` and `Healthy`.

`cluster/install-config.example.yaml` is the verified single-node install configuration. Copy it outside the
repository, fill in the pull secret and SSH key, and run `openshift-install create cluster`. It pins one
availability zone, so it needs a single NAT gateway Elastic IP.

== Verify every cluster

[source,bash]
----
make -C automation verify
----

Every line must print `PASS`. Fix any `FAIL` before participants arrive.

== Day of class

* Share the Showroom URL (`oc -n {showroom_namespace} get route showroom`), the console URL, the `{lab_user}`
  password (from the Secret above) and a MaaS API key per participant.
* Check that the keys can use the model the guide names: `curl -s https://{maas_host}/v1/models -H "Authorization: Bearer <key>"`.
  If the model differs from `{maas_model}`, change `maas_model` in `content/antora.yml` on an event branch.
* The Web Terminal stops when idle and loses its home directory; participants re-run the setup block on the
  prerequisites page.
* ZTVP's Compliance Operator remediation sets `accessTokenInactivityTimeout: 10m` on the cluster OAuth config, so a
  Web Terminal left idle for 10 minutes answers `Unauthorized` until it is reopened. Check with
  `oc get oauth cluster -o jsonpath='{.spec.tokenConfig}'`.
* The chart repository is third-party and still changing. The guide pins chart {chart_version}; check
  `helm search repo openshell-ztm-demo -l` before an event.

== Remove the lab

As cluster-admin, look before you delete:

[source,bash]
----
oc get subscription web-terminal -n openshift-operators -o jsonpath='{.metadata.labels}'
oc get oauth cluster -o jsonpath='{.spec.identityProviders[*].name}'
----

On an RHDP order, deleting the cluster removes everything. Elsewhere, `make -C automation teardown` deletes the lab
Applications and what they created (the ZTVP Pattern is kept on purpose). Then remove the
`openshell-lab-htpasswd` identity provider entry, the Secret of the same name in `openshift-config`, and the
ClusterRoleBinding `openshell-lab-participant`. The chart leaves the Vault role and policy `openshell-admin` and
the NetworkPolicy `allow-openshell-to-vault` in `vault`; remove them with `vault delete auth/hub/role/openshell-admin`
and `vault policy delete openshell-admin` in `vault-0`, and `oc delete networkpolicy allow-openshell-to-vault -n vault`.
