= モジュール 1: カタログから OpenShell をデプロイする
:navtitle: モジュール 1: OpenShell のデプロイ

プラットフォームチームは、チームごとに大量の YAML を用意するのではなく、AI エージェントをクラスターに配置するためのサポートされた単一の方法を求めています。このモジュールでは、OpenShift Developer Catalog に表示される Helm チャートとして
OpenShell をインストールし、*1 回のインストールで何が作成され、API キーはどこに格納されるのか?* という問いに答えます。

チャートリポジトリーを登録し、ゲートウェイが Keycloak に到達するために必要な信頼を与え、リリースをインストールして、キーが Vault に格納されたことを確認します。

.Helm と Developer Catalog を初めて使用する場合
[%collapsible]
====
* *Helm チャート*: 1 つのリリースとしてインストールおよび追跡される、Kubernetes マニフェストのパッケージ。
* *HelmChartRepository*: チャートリポジトリーを Developer Catalog に表示させる OpenShift リソース。
* *Helm フック*: メインリソースの前後など、インストールの決まった時点で実行される Job。
* *ExternalSecret*: External Secrets Operator が読み取り、Vault の値を Kubernetes Secret にコピーするためのリソース。
* *OIDC 発行者 (issuer)*: ゲートウェイが受け入れる署名付きトークンを発行する Keycloak レルムの URL。
====

== 技術的な背景

チャート `openshell-ztm-demo` は NVIDIA の OpenShell Helm チャートをラップし、ZTVP との連携を追加します。1 回の
`helm install` は 3 つのフェーズで実行されます。

[cols="1,3",options="header"]
|===
| フェーズ | 実行される内容

| インストール前フック
| CRD インストーラー Job が、Vault のポリシーとロール `openshell-admin`（`vault-0` 内で `vault` を実行して作成）、`{lab_namespace}` から Vault への到達を許可する NetworkPolicy、および `sandboxes.agents.x-k8s.io` CRD を作成します。次に、Job `vault-seed-maas` がそのロールで Vault にログインし（認証マウント `hub`）、キーを `secret/hub/infra/openshell/maas` に書き込みます
| メインリソース
| ゲートウェイの StatefulSet と Service、ポリシーの ConfigMap、ExternalSecret `maas-api-key-es`、ClusterSPIFFEID、および Kubernetes Secret `maas-api-key`
| インストール後フック
| Job `keycloak-client-setup` が Keycloak に `openshell-gateway` クライアントを作成します。Job `pi-sandbox-setup` がサンドボックスを作成し、MaaS プロバイダーを登録して、ゼロトラストポリシーを適用します
|===

ゲートウェイは起動時に Keycloak も確認します (OIDC ディスカバリー)。このクラスターの Route は OpenShift Ingress Operator の証明書を使用しており、この証明書は公的に信頼されていません。そのため、その CA を ConfigMap でゲートウェイに渡します。チャートのデフォルトの発行者は別のクラスターを指しているため、発行者もこのクラスターの Keycloak に設定します。

デモのゲートウェイは匿名の呼び出し元を受け入れ、管理者として扱います（モジュール 8 で確認します）。チャートはゲートウェイをパブリック Route で公開しますが、このラボでは Route を無効にして NetworkPolicy を追加します。これにより、ゲートウェイに到達できるのはラボの namespace と Web Terminal の namespace のみになります。

== 学習目標

* Developer Catalog にチャートが表示されるように、Helm チャートリポジトリーを登録する。
* このクラスターに合った発行者と CA を指定し、パブリック Route なしで OpenShell リリースをインストールする。
* NetworkPolicy を使用して、ゲートウェイへのネットワークアクセスを制限する。
* リリースが作成する各 Pod とフック Job を特定する。
* MaaS キーが Vault に到達し、External Secrets によって同期されたことを確認する。

== 演習 1: チャートリポジトリーを登録する

インストール前の時点では、OpenShell に関するものは何も存在しません。それを確認してから、リポジトリーを登録します。

[source,bash,role="execute",subs="attributes+"]
----
oc get service {release_name} -n {lab_namespace}
----

期待される結果: namespace または Service について `Error from server (NotFound)` が表示されます。ゲートウェイはまだ存在しないため、CLI の接続先はありません。

[source,yaml,subs="attributes+"]
----
kind: HelmChartRepository
metadata:
  name: openshell-ztm-demo            # <1>
spec:
  connectionConfig:
    url: {chart_repo_url}   # <2>
----
<1> *Name*（名前）: コンソールがこのリポジトリーに使用する、クラスタースコープの名前。
<2> *URL*: コンソールが `index.yaml`（チャートバージョンの一覧）を取得する場所。

[source,bash,role="execute",subs="attributes+"]
----
cat <<'EOF' | oc apply -f -
apiVersion: helm.openshift.io/v1beta1
kind: HelmChartRepository
metadata:
  name: openshell-ztm-demo
spec:
  name: OpenShell ZTM Demo
  connectionConfig:
    url: {chart_repo_url}
EOF
helm search repo openshell-ztm-demo/openshell-ztm-demo --version {chart_version}
----

期待される結果: `helmchartrepository.helm.openshift.io/openshell-ztm-demo created`（または `unchanged`）、続いて 1 行 `openshell-ztm-demo/openshell-ztm-demo  {chart_version}  {openshell_version}` が表示されます。インストールするチャートのバージョンは固定されているため、後からチャートの新しいリリースが公開されてもラボには影響しません。

NOTE: OpenShift {ocp_version} では HelmChartRepository に `status` フィールドがないため、確認できる `Ready`
条件はありません。下記のカタログ表示と `helm search` が証拠になります。

GUI での表示: コンソールの
link:https://console-openshift-console.{cluster_domain}/catalog/ns/{lab_namespace}?catalogType=HelmChart&keyword=openshell[{lab_namespace} の Helm Charts カタログ^]
を開きます（パースペクティブは *Core platform*（コアプラットフォーム）、ブレッドクラムは *Software Catalog*（ソフトウェアカタログ） > *Helm Charts*（Helm チャート））。
*Openshell Ztm Demo* タイルが表示され、*Chart Repositories*（チャートリポジトリー）の下にフィルター *OpenShell ZTM Demo (1)* が表示されます。このタイルからインストールすることもできますが、演習 3 の OpenShift 固有の 2 つの設定がフォームにないため、このラボでは CLI からインストールします。

== 演習 2: namespace と Keycloak の CA を準備する

[source,bash,role="execute",subs="attributes+"]
----
oc create namespace {lab_namespace} --dry-run=client -o yaml | oc apply -f -
oc get configmap default-ingress-cert -n openshift-config-managed -o jsonpath='{.data.ca-bundle\.crt}' > /tmp/ingress-ca.crt
oc create configmap keycloak-ingress-ca -n {lab_namespace} --from-file=ca.crt=/tmp/ingress-ca.crt --dry-run=client -o yaml | oc apply -f -
grep -c 'BEGIN CERTIFICATE' /tmp/ingress-ca.crt
----

期待される結果: namespace と ConfigMap が `created`（または `configured`）となり、カウントは `2` または `3` になります。OpenShift のデフォルトの Ingress 証明書の場合は `2` で、ワイルドカードの Route 証明書と、それに署名した Ingress Operator の CA です。RHDP クラスターは公開証明書を提供するため `3` になり、ワイルドカード証明書とその上位にある 2 つの中間 CA です。どちらのバンドルでも、ゲートウェイは Keycloak の Route を検証できます。

次に、ゲートウェイ Pod へのトラフィックを、ラボの namespace（スーパーバイザー、サンドボックス、セットアップ Job）と、Web Terminal が実行される `openshift-terminal` からのみ許可します。

[source,bash,role="execute",subs="attributes+"]
----
cat <<'EOF' | oc apply -f -
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: gateway-ingress
  namespace: {lab_namespace}
spec:
  podSelector:
    matchLabels:
      app.kubernetes.io/name: openshell
  policyTypes: [Ingress]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: {lab_namespace}
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: openshift-terminal
EOF
----

期待される結果: `networkpolicy.networking.k8s.io/gateway-ingress created`（または `unchanged`）が表示されます。モジュール 2 で、別の namespace からこれをテストします。

まとめ: この CA がないと、ゲートウェイの OIDC ディスカバリーが起動時に失敗し、ゲートウェイ Pod がクラッシュループします。

== 演習 3: リリースをインストールする

この行だけを単独で実行し、プロンプトで MaaS API キーを入力または貼り付けます。入力内容は表示されません。

[source,bash,role="execute",subs="attributes+"]
----
read -rs -p "MaaS API key: " MAAS_API_KEY; echo "key length: ${#MAAS_API_KEY}"
----

期待される結果: ``key length: `` に続いてキーの長さ（0 以外の数値）が表示されます。これにより、キー自体を表示せずに変数が設定されたことを確認できます。

IMPORTANT: プロンプトの行は別々に実行してください。次のブロックと一緒に貼り付けると、`read` は貼り付けられた次の行をキーとして読み取ってしまいます。

続いてインストールします。最後の行で、シェルからキーを削除します。

[source,bash,role="execute",subs="attributes+"]
----
DOMAIN=$(oc get ingresses.config.openshift.io cluster -o jsonpath='{.spec.domain}')
helm install {release_name} openshell-ztm-demo/openshell-ztm-demo --version {chart_version} \
  -n {lab_namespace} \
  --set maas.apiKey="$MAAS_API_KEY" \
  --set maas.model={maas_model} \
  --set vault.enabled=true \
  --set openshell.server.oidc.issuer=https://keycloak.$DOMAIN/realms/{keycloak_realm} \
  --set openshell.server.oidc.caConfigMapName=keycloak-ingress-ca \
  --set openshell.openshiftRoute.enabled=false \
  --wait --timeout 10m | head -6
unset MAAS_API_KEY
----

期待される結果: 約 1 分後に `STATUS: deployed` と `REVISION: 1` が表示されます。

== 演習 4: インストールで作成されたものを特定する

[source,bash,role="execute",subs="attributes+"]
----
oc get pods -n {lab_namespace}
----

期待される結果: 5 つの Pod が表示されます。ゲートウェイ `{release_name}-0` とスーパーバイザー `os-supervisor-…` は
`1/1 Running`、サンドボックス `default--{sandbox_name}` は `1/1 Running`、`keycloak-client-setup-1-…`
と `pi-sandbox-setup-1-…` は `Completed` です。

[cols="1,3",options="header"]
|===
| Pod | 役割

| `{release_name}-0`
| ゲートウェイ (StatefulSet): CLI の通信先となる gRPC API
| `os-supervisor-…`
| スーパーバイザー: ネットワーク境界を適用し、リゾルバートークンを実際の認証情報に置き換えます
| `default--{sandbox_name}`
| Pi エージェントが実行されるサンドボックス（`default` はワークスペース）
| `keycloak-client-setup-1-…`
| `openshell-gateway` Keycloak クライアントを作成したフック Job
| `pi-sandbox-setup-1-…`
| サンドボックスを作成し、そのポリシーを適用したフック Job
|===

次に、ゲートウェイがこのクラスターの Keycloak に到達したこと、およびキーが Vault に格納されていることを確認します。

[source,bash,role="execute",subs="attributes+"]
----
oc logs -n {lab_namespace} {release_name}-0 | grep -o 'JWKS keys loaded.*'
oc get externalsecret maas-api-key-es -n {lab_namespace}
----

期待される結果: `JWKS keys loaded count=1`（ゲートウェイが TLS 経由で Keycloak の署名鍵を取得した）が表示され、ExternalSecret には `SecretSynced` と `True` が表示されます。これは、External Secrets が Vault からキーを読み戻したことを示します。

.この演習のスクリプトによるアサーション
[%collapsible]
====
[source,bash,subs="attributes+"]
----
(
  set -e
  [ "$(oc get pods -n {lab_namespace} --field-selector=status.phase=Running --no-headers | wc -l)" -ge 3 ] || { echo "FAIL: fewer than 3 running pods"; exit 1; }
  oc get externalsecret maas-api-key-es -n {lab_namespace} -o jsonpath='{.status.conditions[0].status}' | grep -qx True || { echo "FAIL: ExternalSecret not synced"; exit 1; }
  oc logs -n {lab_namespace} {release_name}-0 | grep -q 'JWKS keys loaded' || { echo "FAIL: gateway did not load Keycloak keys"; exit 1; }
  echo PASS
)
----
====

== 証拠のチェックポイント

* どのフックがキーを Vault に書き込みましたか? また、そのフックがログインできない場合はどうなりますか?
* ゲートウェイに `keycloak-ingress-ca` ConfigMap が必要だったのはなぜですか?
* Helm の値だけでなく Vault がキーを提供するようになったことを証明するリソースはどれですか?

.解答
[%collapsible]
====
* インストール前の Job `vault-seed-maas` です。この Job は、チャートのインストーラー Job が直前に作成した `openshell-admin` ロールを使用します。ログインに失敗した場合は警告を出力して終了コード 0 で終了するため、インストール自体は Kubernetes Secret だけで成功します。両者の違いは ExternalSecret のステータスで判別できます。
* ゲートウェイは起動時に、Keycloak のディスカバリードキュメントと署名鍵を取得します。Keycloak の Route は
  Ingress Operator の証明書を使用しており、この証明書はどの公的 CA によっても署名されていません。そのため ConfigMap がないと TLS チェックが失敗し、ゲートウェイは終了します。
* `SecretSynced True` となっている ExternalSecret `maas-api-key-es` です。なお、チャートは Helm の値から直接、Secret `maas-api-key` にもキーを書き込みます。External Secrets は Vault のコピーをその Secret にマージします。
====
