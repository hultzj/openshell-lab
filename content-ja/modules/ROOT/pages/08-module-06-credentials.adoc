= モジュール 6: 認証情報のセキュリティー
:navtitle: モジュール 6: 認証情報のセキュリティー

エージェントに API キーを渡す一般的な方法は環境変数ですが、その場合、エージェントはキーを出力したり、ログに記録したり、送信したりできます。このモジュールでは、*エージェントは LLM キーを参照できるか、また、エージェントが保持しているものは盗む価値があるか?* という問いに答えます。

サンドボックス内でキーを探し、境界を経由してプレースホルダーを使用し、その後、同じプレースホルダーを外部から試します。

.境界での認証情報の解決を初めて使用する場合
[%collapsible]
====
* *プロバイダー*: 1 つのアップストリームサービス（ここでは MaaS）の認証情報を保持する OpenShell のレコード。
* *リゾルバートークン*: サンドボックスからキーの代わりに見えるプレースホルダー `openshell:resolve:env:…`。
* *境界*: スーパーバイザーの送信プロキシー。許可されたリクエストについて、プレースホルダーをキーに置き換えます。
====

== 技術的な背景

[cols="1,3",options="header"]
|===
| 段階 | キーの所在

| インストール
| Helm の値が Vault (`secret/hub/infra/openshell/maas`) と Secret `maas-api-key` に格納されます
| セットアップ
| セットアップ Job が、`maas` プロバイダーの認証情報としてキーをゲートウェイに登録します
| ランタイム
| サンドボックスはリゾルバートークンのみを受け取ります。スーパーバイザーが、`{maas_host}` 宛てのリクエストにキーを付加します
|===

== 学習目標

* サンドボックスの環境に、実際のキーがどのような形でも存在しないことを示す。
* プレースホルダーが境界を経由した場合には機能し、それ以外のすべての場所では失敗することを示す。

== 演習 1: サンドボックス内でキーを探す

[source,bash,role="execute",subs="attributes+"]
----
openshell sandbox exec {sandbox_name} < /dev/null -- bash -c 'env | grep -i maas; env | grep -c "sk-"'
----

期待される結果: 1 行の `MAAS_API_KEY=openshell:resolve:env:v…_MAAS_API_KEY` とカウント `0` が表示されます。サンドボックスの環境のどこにも `sk-` の値はありません。

== 演習 2: 境界を経由してプレースホルダーを使用する

[source,bash,role="execute",subs="attributes+"]
----
openshell sandbox exec {sandbox_name} < /dev/null -- bash -c 'curl -s -o /dev/null -w "MaaS HTTP %\{http_code}\n" --max-time 5 https://{maas_host}/v1/models -H "Authorization: Bearer $MAAS_API_KEY"'
----

期待される結果: `MaaS HTTP 200` が表示されます。リクエストはプレースホルダーを持ってサンドボックスを出ましたが、MaaS は実際のキーを受け取りました。

== 演習 3: 別の場所でプレースホルダーを試す

NOTE: どちらの試行も失敗します。これは想定どおりです。プレースホルダーを盗んだ攻撃者が試みるであろう操作を再現しています。

まず、サンドボックス内から別の API に対して試します。

[source,bash,role="execute",subs="attributes+"]
----
openshell sandbox exec {sandbox_name} < /dev/null -- bash -c 'curl -sS --max-time 5 https://api.openai.com/v1/models -H "Authorization: Bearer $MAAS_API_KEY"; echo "exit=$?"'
----

期待される結果: `curl: (7) Failed to connect to api.openai.com` と `exit=7` が表示されます。許可リストにないホストに向けて、プレースホルダーがサンドボックスの外に出ることはありません。

次に、プレースホルダーをサンドボックスの外にコピーし、境界の外にある Web Terminal から
MaaS に直接送信します。

[source,bash,role="execute",subs="attributes+"]
----
TOKEN=$(openshell sandbox exec {sandbox_name} < /dev/null -- printenv MAAS_API_KEY 2>/dev/null | grep '^openshell:resolve')
echo "stolen: ${TOKEN:0:30}..."
curl -s -w "\nHTTP %\{http_code}\n" --max-time 10 https://{maas_host}/v1/models -H "Authorization: Bearer $TOKEN" | tail -c 160
----

期待される結果: `stolen: openshell:resolve:env:v…` に続いて、キーは `expected to start
with 'sk-'` であるという `auth_error` と `HTTP 401` が表示されます。演習 2 で `HTTP 200` を得たのと同じ文字列が、ここでは役に立ちません。

まとめ: エージェントがキーを使用できるのは、バインドされている 1 つのサービスに対してのみであり、しかもサンドボックス内からのみです。

== 証拠のチェックポイント

* このクラスターで実際のキーを読み取ることができるのは依然として誰ですか? また、それが許容されるのはなぜですか?
* 攻撃者がキーを使用するには、プレースホルダー以外に何が必要ですか?

.解答
[%collapsible]
====
* クラスター管理者です。Vault または Secret `maas-api-key` から読み取れます（モジュール 7 でその先頭の数文字を読み取ります）。境界はエージェントからキーを保護するものであり、プラットフォームの管理者から保護するものではありません。
* このサンドボックス内で実行され、スーパーバイザーを介して MaaS ホストを呼び出すコードが必要です。プレースホルダーだけでは何もできません。
====
