= 모듈 5: 파일 시스템 제로 트러스트
:navtitle: 모듈 5: 파일 시스템 제로 트러스트

어디에나 쓸 수 있는 에이전트는 바이너리를 심거나, DNS 설정을 변경하거나, 아무도 보지 않는 곳에 백도어를 남길 수
있습니다. 이 모듈은 다음 질문에 답합니다. *에이전트가 허용된 경로 밖에서 읽거나 쓸 수 있는가? 그리고 이를 막는
것이 일반 파일 권한이 아니라 커널인가?*

정책이 허용하는 위치에 쓰고, 허용하지 않는 경로를 시도한 다음, 한 번의 비교로 Landlock과 일반 Unix 권한을
구분합니다.

.Landlock이 처음이신가요?
[%collapsible]
====
* *Landlock* — 프로세스가 자신의 파일 접근을 스스로 제한할 수 있게 하는 Linux 보안 모듈(커널 5.13부터)입니다. 커널이 이를 강제 적용합니다.
* *LSM* — Linux Security Module로, SELinux와 Landlock이 연결되는 커널 프레임워크입니다.
* *DAC* — 임의 접근 제어(discretionary access control)로, 일반적인 소유자/그룹/기타 권한 비트입니다.
* *EACCES* — 커널이 반환하는 "Permission denied" 오류입니다.
====

== 기술적 배경

게이트웨이가 보고하는 샌드박스 정책(`openshell policy get {sandbox_name} --full`)은 다음과 같습니다.

[source,yaml]
----
filesystem_policy:
  read_only:  [/bin, /usr, /lib, /proc, /dev/urandom, /app, /etc, /var/log]
  read_write: [/sandbox, /tmp, /dev/null]
landlock:
  compatibility: best_effort
----

그 외의 모든 것은 에이전트에게 보이지 않습니다. ``best_effort``는 Landlock이 없는 커널에서도 샌드박스가 시작된다는
뜻이므로, 마지막 실습에서는 이 클러스터에서 Landlock이 실제로 강제 적용되고 있음을 증명합니다.

에이전트는 OpenShift가 할당한 non-root UID로 실행됩니다. 이 점이 중요합니다. ``/etc``와 ``/usr``는 root 소유이므로
일반 권한만으로도 그곳에 대한 일부 쓰기가 차단됩니다. 실습 3에서는 일반 권한이 쓰기를 *허용하는* 경로를 사용합니다.

== 학습 목표

* 허용된 경로에서 읽기와 쓰기가 성공함을 보여 줍니다.
* 허용된 경로 밖에서 쓰기와 목록 조회가 실패함을 보여 줍니다.
* 거부를 일으키는 것이 DAC가 아니라 Landlock임을 증명합니다.

== 실습 1: 허용된 경로 사용

[source,bash,role="execute",subs="attributes+"]
----
openshell sandbox exec {sandbox_name} < /dev/null -- bash -c '
echo "This is allowed" > /sandbox/test.txt && cat /sandbox/test.txt
echo "Temp file" > /tmp/test.txt && cat /tmp/test.txt
ls /usr/bin/node; cat /etc/hostname'
----

예상 결과: `This is allowed`, `Temp file`, `/usr/bin/node`, 그리고 호스트 이름 ``default--{sandbox_name}``이 표시됩니다.

== 실습 2: 거부된 경로 시도

NOTE: 아래의 모든 명령은 ``Permission denied``로 실패합니다. 이는 예상된 동작입니다.

[source,bash,role="execute",subs="attributes+"]
----
openshell sandbox exec {sandbox_name} < /dev/null -- bash -c '
echo hacked > /etc/test; cp /dev/null /usr/bin/node; touch /etc/shadow
ls /; mkdir -p /home/sandbox; ls /opt'
----

예상 결과: `/etc/test: Permission denied`, `cannot create regular file '/usr/bin/node': Permission
denied`, `cannot touch '/etc/shadow': Permission denied`, `cannot open directory '/': Permission denied`,
`cannot create directory '/home/sandbox': Permission denied`,
``cannot open directory '/opt': Permission denied``가 표시됩니다.

== 실습 3: Landlock임을 증명

`/tmp`, `/var/tmp`, ``/dev/shm``은 권한 비트가 같습니다. 모두 sticky 비트가 설정된 전체 쓰기 가능(world-writable) 디렉터리입니다.
일반 권한은 이들을 똑같이 취급합니다. 정책에 포함된 것은 ``/tmp``뿐입니다.

[source,bash,role="execute",subs="attributes+"]
----
openshell sandbox exec {sandbox_name} < /dev/null -- bash -c '
stat -c "%A %U %n" / /tmp /var/tmp /dev/shm
for d in /tmp /var/tmp /dev/shm; do echo probe > $d/probe && echo "$d: write OK" || echo "$d: write DENIED"; done'
----

예상 결과: `/tmp`, `/var/tmp`, ``/dev/shm``은 모두 ``drwxrwxrwt root``로 표시되고, ``/``는
`dr-xr-xr-x`(누구나 목록을 조회할 수 있음)로 표시됩니다. 그다음 `/tmp: write OK`, `/var/tmp: write DENIED`,
``/dev/shm: write DENIED``가 표시됩니다. 권한은 같은데 결과가 다릅니다. 유일한 차이는 커널의 Landlock 규칙 집합입니다. 실습 2의
``ls /``도 마찬가지로, DAC라면 허용했을 동작입니다.

요약: 에이전트에게는 쓰기 가능한 디렉터리가 두 개만 보이며, Unix 권한이 막지 않는 곳에서도 커널이 이를 강제 적용합니다.

.이 실습의 스크립트 검증
[%collapsible]
====
[source,bash,subs="attributes+"]
----
(
  openshell sandbox exec {sandbox_name} < /dev/null -- bash -c 'echo x > /tmp/probe' >/dev/null 2>&1 || { echo "FAIL: /tmp not writable"; exit 1; }
  openshell sandbox exec {sandbox_name} < /dev/null -- bash -c 'echo x > /var/tmp/probe' >/dev/null 2>&1 && { echo "FAIL: /var/tmp writable, Landlock not enforcing"; exit 1; }
  echo PASS
)
----
====

== 증거 확인

* 여기서 `/etc/test` 거부만으로는 Landlock의 증거로 약한 이유는 무엇입니까?
* ``compatibility: best_effort``는 오래된 커널을 사용하는 클러스터에 대해 무엇을 의미합니까?

.정답
[%collapsible]
====
* ``/etc``는 root 소유이고 에이전트의 UID는 root가 아니므로, 일반 권한만으로도 그 쓰기는 거부됩니다.
  ``/var/tmp``와 ``/dev/shm``의 결과, 그리고 ``ls /``는 Landlock으로만 설명되는 거부입니다.
* 샌드박스가 파일 시스템 제한 없이 시작됩니다. 새 클러스터에서는 정책에 의존하기 전에 실습 3의 검사를
  실행하십시오.
====
