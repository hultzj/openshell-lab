= 모듈 1: 카탈로그에서 OpenShell 배포
:navtitle: 모듈 1: OpenShell 배포

플랫폼 팀은 팀마다 YAML 더미를 쌓는 대신, AI 에이전트를 클러스터에 올리는 지원되는 단일 경로를 원합니다.
이 모듈에서는 OpenShift Developer Catalog에 표시되는 Helm 차트로 OpenShell을 설치하고, 다음 질문에
답합니다. *한 번의 설치로 무엇이 생성되며, API 키는 어디로 가는가?*

차트 리포지토리를 등록하고, 게이트웨이가 Keycloak에 접속하는 데 필요한 신뢰를 부여하고, 릴리스를 설치한 다음,
키가 Vault에 저장되었는지 확인합니다.

.Helm과 Developer Catalog가 처음이신가요?
[%collapsible]
====
* *Helm 차트* — 하나의 릴리스로 설치되고 추적되는 Kubernetes 매니페스트 패키지입니다.
* *HelmChartRepository* — 차트 리포지토리를 Developer Catalog에 표시하는 OpenShift 리소스입니다.
* *Helm 훅* — 주요 리소스 생성 전후와 같이 설치 과정의 정해진 시점에 실행되는 Job입니다.
* *ExternalSecret* — External Secrets Operator가 읽어 Vault 값을 Kubernetes 시크릿으로 복사하는 데 사용하는 리소스입니다.
* *OIDC 발급자(issuer)* — 게이트웨이가 서명된 토큰을 수락하는 Keycloak 렐름 URL입니다.
====

== 기술적 배경

차트 ``openshell-ztm-demo``는 NVIDIA의 OpenShell Helm 차트를 감싸고 ZTVP 연결 구성을 추가합니다. 한 번의
``helm install``은 세 단계로 실행됩니다.

[cols="1,3",options="header"]
|===
| 단계 | 실행되는 항목

| 사전 설치(pre-install) 훅
| CRD 설치 Job이 Vault 정책 및 역할 `openshell-admin`(`vault-0` 안에서 ``vault``를 실행하여 생성), ``{lab_namespace}``가 Vault에 접속할 수 있도록 하는 NetworkPolicy, 그리고 `sandboxes.agents.x-k8s.io` CRD를 생성합니다. 그런 다음 Job ``vault-seed-maas``가 해당 역할(인증 마운트 `hub`)로 Vault에 로그인하여 키를 ``secret/hub/infra/openshell/maas``에 씁니다
| 주요 리소스
| 게이트웨이 StatefulSet 및 Service, 정책 ConfigMap, ExternalSecret `maas-api-key-es`, ClusterSPIFFEID, Kubernetes 시크릿 `maas-api-key`
| 사후 설치(post-install) 훅
| Job ``keycloak-client-setup``이 Keycloak에 `openshell-gateway` 클라이언트를 생성합니다. Job ``pi-sandbox-setup``이 샌드박스를 생성하고, MaaS 프로바이더를 등록하고, 제로 트러스트 정책을 적용합니다
|===

게이트웨이는 시작할 때 Keycloak도 확인합니다(OIDC 디스커버리). 이 클러스터의 Route는 공개적으로 신뢰되지 않는
OpenShift 인그레스 오퍼레이터의 인증서를 사용하므로, ConfigMap으로 해당 CA를 게이트웨이에 제공합니다. 차트의 기본
발급자는 다른 클러스터를 가리키므로, 발급자도 이 클러스터의 Keycloak으로 설정합니다.

데모 게이트웨이는 익명 호출자를 허용하고 이들을 관리자로 취급합니다(모듈 8에서 확인합니다). 차트는 기본적으로
게이트웨이를 공개 Route로 게시하지만, 이 랩에서는 Route를 끄고 NetworkPolicy를 추가하여 랩 네임스페이스와
Web Terminal 네임스페이스만 게이트웨이에 접근할 수 있도록 합니다.

== 학습 목표

* Developer Catalog에 차트가 표시되도록 Helm 차트 리포지토리를 등록합니다.
* 이 클러스터에 맞는 발급자와 CA를 사용하고 공개 Route 없이 OpenShell 릴리스를 설치합니다.
* NetworkPolicy로 게이트웨이에 대한 네트워크 접근을 제한합니다.
* 릴리스가 생성하는 각 파드와 훅 Job을 식별합니다.
* MaaS 키가 Vault에 저장되었고 External Secrets가 이를 동기화했는지 확인합니다.

== 실습 1: 차트 리포지토리 등록

설치 전에는 OpenShell 관련 리소스가 전혀 없습니다. 이를 확인한 다음 리포지토리를 등록합니다.

[source,bash,role="execute",subs="attributes+"]
----
oc get service {release_name} -n {lab_namespace}
----

예상 결과: 네임스페이스 또는 서비스에 대해 ``Error from server (NotFound)``가 표시됩니다. 아직 게이트웨이가 없으므로
CLI가 통신할 대상이 없습니다.

[source,yaml,subs="attributes+"]
----
kind: HelmChartRepository
metadata:
  name: openshell-ztm-demo            # <1>
spec:
  connectionConfig:
    url: {chart_repo_url}   # <2>
----
<1> *Name*(이름) — 콘솔이 이 리포지토리에 사용하는 클러스터 범위 이름입니다.
<2> *URL* — 콘솔이 차트 버전 목록인 ``index.yaml``을 가져오는 위치입니다.

[source,bash,role="execute",subs="attributes+"]
----
cat <<'EOF' | oc apply -f -
apiVersion: helm.openshift.io/v1beta1
kind: HelmChartRepository
metadata:
  name: openshell-ztm-demo
spec:
  name: OpenShell ZTM Demo
  connectionConfig:
    url: {chart_repo_url}
EOF
helm search repo openshell-ztm-demo/openshell-ztm-demo --version {chart_version}
----

예상 결과: `helmchartrepository.helm.openshift.io/openshell-ztm-demo created`(또는 `unchanged`),
그다음 한 행 ``openshell-ztm-demo/openshell-ztm-demo  {chart_version}  {openshell_version}``이 표시됩니다. 설치할
차트 버전이 고정되어 있으므로 이후에 차트가 새로 릴리스되어도 랩에는 영향이 없습니다.

NOTE: OpenShift {ocp_version}에서는 HelmChartRepository에 `status` 필드가 없으므로 확인할 `Ready`
조건이 없습니다. 아래의 카탈로그 목록과 `helm search` 결과가 증거입니다.

GUI 보기: 콘솔의
link:https://console-openshift-console.{cluster_domain}/catalog/ns/{lab_namespace}?catalogType=HelmChart&keyword=openshell[{lab_namespace}용 Helm Charts 카탈로그^]를
엽니다(관점 *Core platform*(코어 플랫폼), 탐색 경로 *Software Catalog*(소프트웨어 카탈로그) > *Helm Charts*(Helm 차트)). *Openshell Ztm Demo* 타일이 표시되고,
*Chart Repositories*(차트 리포지토리) 아래에 *OpenShell ZTM Demo (1)* 필터가 나타납니다. 이 타일에서 설치할 수도 있지만,
실습 3의 OpenShift 전용 설정 두 가지가 양식에 없으므로 이 랩에서는 CLI로 설치합니다.

== 실습 2: 네임스페이스와 Keycloak CA 준비

[source,bash,role="execute",subs="attributes+"]
----
oc create namespace {lab_namespace} --dry-run=client -o yaml | oc apply -f -
oc get configmap default-ingress-cert -n openshift-config-managed -o jsonpath='{.data.ca-bundle\.crt}' > /tmp/ingress-ca.crt
oc create configmap keycloak-ingress-ca -n {lab_namespace} --from-file=ca.crt=/tmp/ingress-ca.crt --dry-run=client -o yaml | oc apply -f -
grep -c 'BEGIN CERTIFICATE' /tmp/ingress-ca.crt
----

예상 결과: 네임스페이스와 ConfigMap이 `created`(또는 `configured`)로 표시되고, 개수는 `2` 또는 ``3``입니다.
OpenShift의 기본 인그레스 인증서를 사용하면 ``2``입니다. 와일드카드 Route 인증서와 이를 서명한 인그레스 오퍼레이터
CA입니다. RHDP 클러스터는 공개 인증서를 제공하므로 ``3``입니다. 와일드카드 인증서와 그 위의 중간 CA 두 개입니다.
어느 번들이든 게이트웨이가 Keycloak의 Route를 검증할 수 있습니다.

이제 랩 네임스페이스(수퍼바이저, 샌드박스, 설정 Job)와 Web Terminal이 실행되는 ``openshift-terminal``에서만
게이트웨이 파드로 트래픽이 들어오도록 허용합니다.

[source,bash,role="execute",subs="attributes+"]
----
cat <<'EOF' | oc apply -f -
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: gateway-ingress
  namespace: {lab_namespace}
spec:
  podSelector:
    matchLabels:
      app.kubernetes.io/name: openshell
  policyTypes: [Ingress]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: {lab_namespace}
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: openshift-terminal
EOF
----

예상 결과: `networkpolicy.networking.k8s.io/gateway-ingress created`(또는 `unchanged`)가 표시됩니다. 모듈 2에서 다른 네임스페이스로부터 이를 테스트합니다.

요약: 이 CA가 없으면 시작 시 게이트웨이의 OIDC 디스커버리가 실패하고 게이트웨이 파드가 크래시 루프에 빠집니다.

== 실습 3: 릴리스 설치

이 줄만 단독으로 실행하고, 프롬프트에 MaaS API 키를 입력하거나 붙여 넣습니다. 입력한 키는 화면에 표시되지 않습니다.

[source,bash,role="execute",subs="attributes+"]
----
read -rs -p "MaaS API key: " MAAS_API_KEY; echo "key length: ${#MAAS_API_KEY}"
----

예상 결과: ``key length: `` 뒤에 키의 길이(0이 아닌 숫자)가 표시됩니다. 키를 화면에 표시하지 않고도 변수가
설정되었음을 알 수 있습니다.

IMPORTANT: 프롬프트 줄은 따로 실행하십시오. 다음 블록과 함께 붙여 넣으면 ``read``가 붙여 넣은 다음 줄을
키로 받아들입니다.

그런 다음 설치합니다. 마지막 줄은 셸에서 키를 제거합니다.

[source,bash,role="execute",subs="attributes+"]
----
DOMAIN=$(oc get ingresses.config.openshift.io cluster -o jsonpath='{.spec.domain}')
helm install {release_name} openshell-ztm-demo/openshell-ztm-demo --version {chart_version} \
  -n {lab_namespace} \
  --set maas.apiKey="$MAAS_API_KEY" \
  --set maas.model={maas_model} \
  --set vault.enabled=true \
  --set openshell.server.oidc.issuer=https://keycloak.$DOMAIN/realms/{keycloak_realm} \
  --set openshell.server.oidc.caConfigMapName=keycloak-ingress-ca \
  --set openshell.openshiftRoute.enabled=false \
  --wait --timeout 10m | head -6
unset MAAS_API_KEY
----

예상 결과: 약 1분 후 ``STATUS: deployed``와 ``REVISION: 1``이 표시됩니다.

== 실습 4: 설치로 생성된 항목 식별

[source,bash,role="execute",subs="attributes+"]
----
oc get pods -n {lab_namespace}
----

예상 결과: 파드 5개가 표시됩니다. 게이트웨이 ``{release_name}-0``과 수퍼바이저 ``os-supervisor-…``는
`1/1 Running`, 샌드박스 ``default--{sandbox_name}``은 ``1/1 Running``이며, ``keycloak-client-setup-1-…``과
``pi-sandbox-setup-1-…``은 ``Completed``입니다.

[cols="1,3",options="header"]
|===
| 파드 | 역할

| `{release_name}-0`
| 게이트웨이(StatefulSet): CLI가 통신하는 gRPC API
| `os-supervisor-…`
| 수퍼바이저: 네트워크 경계를 강제 적용하고 리졸버 토큰을 실제 자격 증명으로 교체
| `default--{sandbox_name}`
| Pi 에이전트가 실행되는 샌드박스(``default``는 워크스페이스)
| `keycloak-client-setup-1-…`
| `openshell-gateway` Keycloak 클라이언트를 생성한 훅 Job
| `pi-sandbox-setup-1-…`
| 샌드박스를 생성하고 정책을 적용한 훅 Job
|===

이제 게이트웨이가 이 클러스터의 Keycloak에 접속했는지, 그리고 키가 Vault에 있는지 확인합니다.

[source,bash,role="execute",subs="attributes+"]
----
oc logs -n {lab_namespace} {release_name}-0 | grep -o 'JWKS keys loaded.*'
oc get externalsecret maas-api-key-es -n {lab_namespace}
----

예상 결과: `JWKS keys loaded count=1`(게이트웨이가 TLS를 통해 Keycloak의 서명 키를 가져옴)이 표시되고,
ExternalSecret에 ``SecretSynced``와 ``True``가 표시됩니다. External Secrets가 Vault에서 키를 다시 읽어 왔다는 뜻입니다.

.이 실습의 스크립트 검증
[%collapsible]
====
[source,bash,subs="attributes+"]
----
(
  set -e
  [ "$(oc get pods -n {lab_namespace} --field-selector=status.phase=Running --no-headers | wc -l)" -ge 3 ] || { echo "FAIL: fewer than 3 running pods"; exit 1; }
  oc get externalsecret maas-api-key-es -n {lab_namespace} -o jsonpath='{.status.conditions[0].status}' | grep -qx True || { echo "FAIL: ExternalSecret not synced"; exit 1; }
  oc logs -n {lab_namespace} {release_name}-0 | grep -q 'JWKS keys loaded' || { echo "FAIL: gateway did not load Keycloak keys"; exit 1; }
  echo PASS
)
----
====

== 증거 확인

* 어떤 훅이 키를 Vault에 썼으며, 그 훅이 로그인하지 못하면 어떻게 됩니까?
* 게이트웨이에 `keycloak-ingress-ca` ConfigMap이 필요했던 이유는 무엇입니까?
* Helm 값뿐 아니라 Vault가 이제 키를 제공한다는 것을 증명하는 리소스는 무엇입니까?

.정답
[%collapsible]
====
* 사전 설치 Job ``vault-seed-maas``이며, 직전에 차트의 설치 Job이 생성한 `openshell-admin` 역할을 사용합니다.
  로그인에 실패하면 경고를 출력하고 0으로 종료하므로, 설치는 Kubernetes 시크릿만 있는 상태로 성공합니다.
  ExternalSecret 상태로 두 경우를 구분할 수 있습니다.
* 게이트웨이는 시작할 때 Keycloak의 디스커버리 문서와 서명 키를 가져옵니다. Keycloak의 Route는 어떤 공개 CA도
  서명하지 않은 인그레스 오퍼레이터의 인증서를 사용하므로, ConfigMap이 없으면 TLS 검사가 실패하고
  게이트웨이가 종료됩니다.
* `SecretSynced True` 상태인 ExternalSecret ``maas-api-key-es``입니다. 차트는 Helm 값에서 키를 직접
  시크릿 ``maas-api-key``에도 쓴다는 점에 유의하십시오. External Secrets는 Vault의 사본을 이 시크릿에 병합합니다.
====
