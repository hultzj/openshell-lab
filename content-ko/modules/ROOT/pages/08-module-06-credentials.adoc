= 모듈 6: 자격 증명 보안
:navtitle: 모듈 6: 자격 증명 보안

에이전트에게 API 키를 주는 일반적인 방법은 환경 변수이며, 그러면 에이전트는 키를 출력하거나, 로그에 남기거나,
외부로 보낼 수 있습니다. 이 모듈은 다음 질문에 답합니다. *에이전트가 LLM 키를 볼 수 있는가? 그리고 에이전트가
가진 것은 훔칠 가치가 있는가?*

샌드박스 안에서 키를 찾아보고, 경계를 통해 자리 표시자를 사용한 다음, 같은 자리 표시자를 외부에서 시도합니다.

.경계 측 자격 증명 해석이 처음이신가요?
[%collapsible]
====
* *프로바이더* — 하나의 업스트림 서비스(여기서는 MaaS)에 대한 자격 증명을 보관하는 OpenShell 레코드입니다.
* *리졸버 토큰* — 샌드박스가 키 대신 보게 되는 자리 표시자 ``openshell:resolve:env:…``입니다.
* *경계* — 허용된 요청에 대해 자리 표시자를 키로 교체하는 수퍼바이저의 egress 프록시입니다.
====

== 기술적 배경

[cols="1,3",options="header"]
|===
| 단계 | 키의 위치

| 설치
| Helm 값이 Vault(`secret/hub/infra/openshell/maas`)와 시크릿 ``maas-api-key``로 전달됩니다
| 설정
| 설정 Job이 키를 `maas` 프로바이더의 자격 증명으로 게이트웨이에 등록합니다
| 런타임
| 샌드박스는 리졸버 토큰만 받습니다. 수퍼바이저가 ``{maas_host}``로 향하는 요청에 키를 첨부합니다
|===

== 학습 목표

* 샌드박스 환경에 실제 키가 어떤 형태로도 존재하지 않음을 보여 줍니다.
* 자리 표시자가 경계를 통해서는 동작하고 그 외의 모든 곳에서는 실패함을 보여 줍니다.

== 실습 1: 샌드박스 안에서 키 찾기

[source,bash,role="execute",subs="attributes+"]
----
openshell sandbox exec {sandbox_name} < /dev/null -- bash -c 'env | grep -i maas; env | grep -c "sk-"'
----

예상 결과: `MAAS_API_KEY=openshell:resolve:env:v…_MAAS_API_KEY` 한 줄과 개수 ``0``이 표시됩니다. 샌드박스 환경
어디에도 `sk-` 값이 없습니다.

== 실습 2: 경계를 통해 자리 표시자 사용

[source,bash,role="execute",subs="attributes+"]
----
openshell sandbox exec {sandbox_name} < /dev/null -- bash -c 'curl -s -o /dev/null -w "MaaS HTTP %\{http_code}\n" --max-time 5 https://{maas_host}/v1/models -H "Authorization: Bearer $MAAS_API_KEY"'
----

예상 결과: ``MaaS HTTP 200``이 표시됩니다. 요청은 자리 표시자를 가진 채로 샌드박스를 떠났고, MaaS는 실제 키를
받았습니다.

== 실습 3: 다른 곳에서 자리 표시자 시도

NOTE: 두 시도 모두 실패합니다. 이는 예상된 동작이며, 자리 표시자를 훔친 공격자가 시도할 만한 방법입니다.

먼저 샌드박스 안에서 다른 API에 대해 시도합니다.

[source,bash,role="execute",subs="attributes+"]
----
openshell sandbox exec {sandbox_name} < /dev/null -- bash -c 'curl -sS --max-time 5 https://api.openai.com/v1/models -H "Authorization: Bearer $MAAS_API_KEY"; echo "exit=$?"'
----

예상 결과: ``curl: (7) Failed to connect to api.openai.com``과 ``exit=7``이 표시됩니다. 자리 표시자는 허용 목록 밖의
호스트를 향해서는 결코 샌드박스를 벗어나지 않습니다.

그런 다음 자리 표시자를 샌드박스 밖으로 복사하여, 경계 밖에 있는 Web Terminal에서 MaaS로 직접 보냅니다.

[source,bash,role="execute",subs="attributes+"]
----
TOKEN=$(openshell sandbox exec {sandbox_name} < /dev/null -- printenv MAAS_API_KEY 2>/dev/null | grep '^openshell:resolve')
echo "stolen: ${TOKEN:0:30}..."
curl -s -w "\nHTTP %\{http_code}\n" --max-time 10 https://{maas_host}/v1/models -H "Authorization: Bearer $TOKEN" | tail -c 160
----

예상 결과: ``stolen: openshell:resolve:env:v…``가 표시된 다음, 키가
``expected to start with 'sk-'``라는 ``auth_error``와 ``HTTP 401``이 표시됩니다. 실습 2에서 ``HTTP 200``을 받은 바로 그 문자열이 여기서는 쓸모가 없습니다.

요약: 에이전트는 키가 바인딩된 단 하나의 서비스에 대해서만, 그리고 샌드박스 안에서만 키를 사용할 수 있습니다.

== 증거 확인

* 이 클러스터에서 여전히 실제 키를 읽을 수 있는 사람은 누구이며, 그것이 허용되는 이유는 무엇입니까?
* 공격자가 키를 사용하려면 자리 표시자 외에 무엇이 필요합니까?

.정답
[%collapsible]
====
* 클러스터 관리자는 Vault 또는 시크릿 ``maas-api-key``에서 키를 읽을 수 있습니다(모듈 7에서 키의 처음 몇 글자를 읽습니다).
  경계는 플랫폼 관리자가 아니라 에이전트로부터 키를 보호합니다.
* 이 샌드박스 안에서 실행되며 수퍼바이저를 통해 MaaS 호스트를 호출하는 코드가 필요합니다. 자리 표시자만으로는 아무것도 할 수 없습니다.
====
