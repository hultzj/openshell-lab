= 모듈 4: 네트워크 제로 트러스트
:navtitle: 모듈 4: 네트워크 제로 트러스트

임의의 호스트에 접속할 수 있는 에이전트는 코드를 어디로든 보내거나, 멀웨어를 가져오거나, 클라우드 메타데이터
서비스에 자격 증명을 요청할 수 있습니다. 이 모듈은 다음 질문에 답합니다. *에이전트가 승인하지 않은 호스트에
접속하거나 승인하지 않은 프로그램을 사용할 수 있는가?*

허용된 호스트와 목록에 없는 호스트를 호출하고, 같은 호스트를 호출하는 두 프로그램을 비교한 다음, 수퍼바이저가
기록하는 감사 이벤트를 확인합니다.

.프로세스 수준의 egress 제어가 처음이신가요?
[%collapsible]
====
* *허용 목록* — 허용되는 유일한 대상입니다. 그 외의 모든 대상은 거부됩니다.
* *바이너리 바인딩* — 규칙이 호스트뿐 아니라 어떤 실행 파일이 엔드포인트를 사용할 수 있는지도 지정합니다.
* *합성 주소* — 샌드박스는 목록에 없는 이름을 수퍼바이저가 거부하는 주소인 ``198.18.0.x``로 해석합니다.
* *OCSF* — Open Cybersecurity Schema Framework로, 수퍼바이저 감사 이벤트의 구조화된 형식입니다.
====

== 기술적 배경

차트의 정책은 세 개의 대상을 허용하며, 각 대상은 지정된 바이너리에만 허용됩니다.

[cols="2,1,2",options="header"]
|===
| 호스트 | 포트 | 허용된 바이너리

| `{maas_host}`
| 443
| `curl`, `node`
| `github.com`, `api.github.com`
| 443
| `git`, `curl`
| `registry.npmjs.org`
| 443
| `npm`, `node`
|===

이는 파드 단위로 결정하는 Kubernetes NetworkPolicy가 아닙니다. OpenShell은 프로세스 단위로 결정합니다.
수퍼바이저는 모든 연결에 대해 호스트 *와* 실행 파일을 함께 검사합니다.

== 학습 목표

* 허용된 호스트는 응답하고 목록에 없는 호스트는 즉시 거부됨을 보여 줍니다.
* 같은 호스트가 한 바이너리에는 허용되고 다른 바이너리에는 거부됨을 보여 줍니다.
* 거부된 연결에 대한 수퍼바이저의 감사 이벤트를 확인합니다.

== 실습 1: 허용된 호스트 호출

[source,bash,role="execute",subs="attributes+"]
----
openshell sandbox exec {sandbox_name} < /dev/null -- bash -c '
curl -s -o /tmp/models.json -w "MaaS HTTP %\{http_code}\n" --max-time 5 https://{maas_host}/v1/models -H "Authorization: Bearer $MAAS_API_KEY"; head -c 200 /tmp/models.json; echo
curl -s -o /dev/null -w "github.com HTTP %\{http_code}\n" --max-time 5 https://github.com'
----

예상 결과: `MaaS HTTP 200` 다음에 ``"id":"{maas_model}"``을 포함한 JSON 모델 목록이 표시되고, 그다음
``github.com HTTP 200``이 표시됩니다. 샌드박스가 리졸버 토큰만 보냈는데도 MaaS는 호출을 수락했습니다.

== 실습 2: 목록에 없는 호스트 호출

[source,bash,role="execute",subs="attributes+"]
----
openshell sandbox exec {sandbox_name} < /dev/null -- bash -c '
for h in https://www.google.com https://example.com https://evil-exfil-server.com/upload http://169.254.169.254/latest/meta-data/; do
  echo "== $h"; curl -sS --max-time 5 -o /dev/null "$h"; echo "exit=$?"
done
getent hosts www.google.com'
----

예상 결과: AWS 메타데이터 주소를 포함한 모든 호출이 `curl: (7) Failed to connect … after 1 ms`(5초 시간 초과가
아니라 수 밀리초)와 ``exit=7``로 실패합니다. ``getent``는 ``www.google.com``이 `198.18.0.x` 합성 주소로
해석됨을 보여 줍니다.

== 실습 3: 같은 호스트, 다른 프로그램

``node``는 MaaS에 접속할 수 있지만, GitHub는 ``git``과 ``curl``에만 바인딩되어 있습니다.

[source,bash,role="execute",subs="attributes+"]
----
openshell sandbox exec {sandbox_name} < /dev/null -- node -e '
const t = (n, u) => fetch(u).then(r => console.log(n, "HTTP", r.status)).catch(e => console.log(n, "ERR", e.cause ? e.cause.code : e.message));
t("node -> github.com", "https://github.com");
t("node -> MaaS", "https://{maas_host}/v1/models");'
----

예상 결과: `node -> github.com ERR EACCES`(이 바이너리에 대해 거부됨)와 `node -> MaaS HTTP 401`
또는 `HTTP 200`(연결은 허용됨. 401은 이 호출이 키를 보내지 않았다는 뜻일 뿐임)이 표시됩니다.

요약: 실습 1에서 ``curl``은 github.com에 접속했지만 ``node``는 접속하지 못했습니다. 규칙은 실행 파일 단위로 적용됩니다.

== 실습 4: 감사 기록 확인

[source,bash,role="execute",subs="attributes+"]
----
openshell logs {sandbox_name} --since 5m | grep 'DENIED' | tail -4
----

예상 결과: ``NET:OPEN [MED] DENIED /usr/bin/curl(…) -> example.com:443 [reason:transparent_tcp_policy_denied]``와
같은 ``OCSF`` 줄이 표시되며, 바이너리, 대상, 이유가 명시됩니다.

.이 실습의 스크립트 검증
[%collapsible]
====
[source,bash,subs="attributes+"]
----
(
  out=$(openshell sandbox exec {sandbox_name} < /dev/null -- curl -s -o /dev/null -w '%\{http_code}' --max-time 5 https://github.com 2>/dev/null | tail -1)
  [ "$out" = 200 ] || { echo "FAIL: allowed host github.com returned '$out'"; exit 1; }
  openshell sandbox exec {sandbox_name} < /dev/null -- curl -s --max-time 5 -o /dev/null https://example.com >/dev/null 2>&1 && { echo "FAIL: example.com was reachable"; exit 1; }
  echo PASS
)
----
====

== 증거 확인

* 거부된 연결이 시간 초과를 기다리지 않고 약 1밀리초 만에 실패한 이유는 무엇입니까?
* 손상된 에이전트가 메타데이터 서비스에서 클라우드 자격 증명을 읽지 못하게 막는 것은 무엇입니까?

.정답
[%collapsible]
====
* 목록에 없는 이름은 합성 주소 ``198.18.0.x``로 해석되고 수퍼바이저가 로컬에서 연결을 거부합니다.
  실제 호스트로는 아무것도 전송되지 않습니다.
* ``169.254.169.254``는 어떤 바이너리의 허용 목록에도 없으므로, 다른 목록에 없는 대상과 마찬가지로 연결이
  거부됩니다.
====
