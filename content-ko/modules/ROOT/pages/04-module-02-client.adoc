= 모듈 2: OpenShell CLI 연결
:navtitle: 모듈 2: CLI 연결

이후의 모든 모듈은 게이트웨이를 통해 샌드박스를 조작하므로, CLI는 게이트웨이에 접속할 수 있어야 하고 다른 누구도
접속할 수 없어야 합니다. 이 모듈은 다음 질문에 답합니다. *클라이언트는 게이트웨이를 어떻게 찾고 신뢰하며, 그 외에 누가 게이트웨이에 접속할 수 있는가?*

게이트웨이의 클러스터 내부 Service를 통해 샌드박스 목록을 조회하고, CLI가 거부하는 동작을 확인한 다음,
인터넷에서도 다른 네임스페이스에서도 게이트웨이에 접속할 수 없음을 확인합니다.

.OpenShell CLI가 처음이신가요?
[%collapsible]
====
* *게이트웨이 엔드포인트* — CLI가 gRPC로 통신하는 HTTPS URL입니다. 여기서는 게이트웨이의 Kubernetes Service입니다.
* *gRPC* — HTTP/2 위에서 동작하는 바이너리 원격 프로시저 호출 프로토콜입니다.
* *Insecure 모드* — 인증서 검증 없이 암호화된 TLS입니다. 게이트웨이 인증서가 차트 자체 CA에서 발급되므로 사용합니다.
* *NetworkPolicy* — 어떤 파드가 어떤 파드에 연결할 수 있는지 제한하는 Kubernetes 규칙입니다.
====

== 기술적 배경

사전 요구 사항 페이지의 설정 블록은 ``~/.openshell-lab.env``에 두 개의 변수를 기록했습니다.
`OPENSHELL_GATEWAY_ENDPOINT=https://{release_name}.{lab_namespace}.svc.cluster.local:8080`(Service이며,
엔드포인트에는 ``https://``가 반드시 포함되어야 함)과 ``OPENSHELL_GATEWAY_INSECURE=true``입니다. Web Terminal은 클러스터
안에서 실행되므로 Service에 직접 접속합니다. 명령의 경로는 CLI → 게이트웨이 Service(TLS) → 게이트웨이 파드 → 수퍼바이저 →
샌드박스입니다. 모듈 1에서는 Route 없이 설치하고 NetworkPolicy ``gateway-ingress``를 추가했습니다.

== 학습 목표

* 게이트웨이를 통해 샌드박스 목록을 조회하고 샌드박스 단계를 확인합니다.
* 엔드포인트에 스킴이 포함되어야 하는 이유와 insecure 모드를 설정하는 이유를 설명합니다.
* 게이트웨이에 공개 엔드포인트가 없으며 다른 네임스페이스로부터의 연결을 거부함을 보여 줍니다.

== 실습 1: 게이트웨이를 통해 샌드박스 목록 조회

[source,bash,role="execute",subs="attributes+"]
----
source ~/.openshell-lab.env
echo "$OPENSHELL_GATEWAY_ENDPOINT"
oc get service {release_name} -n {lab_namespace}
openshell sandbox list
----

예상 결과: 엔드포인트 `https://{release_name}.{lab_namespace}.svc.cluster.local:8080`, 포트가 ``8080/TCP``이고
유형이 ``ClusterIP``인 Service ``{release_name}``이 표시되며, 목록에 ``{sandbox_name}``이 `Ready` 단계로 표시됩니다.
CLI는 `WARN … TLS certificate verification is disabled` 줄도 출력합니다. 이는 여러분이 설정한 insecure 모드 때문입니다.

== 실습 2: CLI가 거부하는 동작 확인

NOTE: 아래 두 명령은 모두 실패합니다. 이는 예상된 동작이며, 각 명령은 CLI가 강제하는 규칙을 하나씩 보여 줍니다.

[source,bash,role="execute",subs="attributes+"]
----
OPENSHELL_GATEWAY_ENDPOINT=${OPENSHELL_GATEWAY_ENDPOINT#https://} openshell sandbox list; echo "exit=$?"
OPENSHELL_GATEWAY_INSECURE=false openshell sandbox list; echo "exit=$?"
----

예상 결과: 첫 번째 명령은 ``gateway URL must start with http:// or https://``와 ``exit=1``로 실패합니다. 두 번째 명령은
``failed to read TLS CA from …/mtls/ca.crt``와 ``exit=1``로 실패합니다. 검증이 켜져 있으면 CLI는 제공받은 적 없는 CA를
찾으며, 인증서를 그냥 신뢰하는 대신 중단합니다.

요약: CLI는 잘못된 엔드포인트와 검증할 수 없는 인증서에 대해 안전하게 실패(fail closed)합니다.

== 실습 3: 그 외에 누가 게이트웨이에 접속할 수 있는지 확인

NOTE: 아래의 프로브는 연결에 실패하는 것이 정상입니다. 그것이 원하는 결과입니다.

[source,bash,role="execute",subs="attributes+"]
----
oc get route -n {lab_namespace}
oc run gateway-probe -n default --rm -i --restart=Never --quiet --image=registry.access.redhat.com/ubi9/ubi-minimal -- \
  curl -sk -o /dev/null --max-time 5 -w '%\{http_code}\n' https://{release_name}.{lab_namespace}.svc.cluster.local:8080; echo "exit=$?"
----

예상 결과: `No resources found in {lab_namespace} namespace.`(공개 Route 없음)가 표시된 다음, `default`
네임스페이스의 프로브 파드가 ``000``과 `exit=28`(curl의 시간 초과)을 출력합니다. NetworkPolicy가 게이트웨이로 향하는
연결을 차단한 것입니다. 반면 같은 Service가 실습 1에서는 Web Terminal에 응답했습니다.

== 증거 확인

* ``default``의 파드는 접속할 수 없는데 Web Terminal은 게이트웨이에 접속할 수 있는 이유는 무엇입니까?
* 프로덕션 환경에서는 insecure 모드 대신 무엇을 구성하겠습니까?

.정답
[%collapsible]
====
* NetworkPolicy ``gateway-ingress``가 ``{lab_namespace}``와 ``openshift-terminal``로부터의 연결만 허용하기 때문입니다.
* CLI가 검증할 수 있는 인증서(클라이언트에 배포된 게이트웨이 CA)를 구성하여 ``OPENSHELL_GATEWAY_INSECURE``를
  설정하지 않은 상태로 두고, 익명 접근 대신 게이트웨이 인증(모듈 8)을 구성합니다.
====
