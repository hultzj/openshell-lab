= 모듈 8: 사용자 인증
:navtitle: 모듈 8: 사용자 인증

지금까지 아무도 여러분이 누구인지 묻지 않았습니다. 모든 CLI 호출은 익명으로 게이트웨이에 도달했습니다. 이 모듈은
다음 질문에 답합니다. *게이트웨이는 사용자 ID를 검증하는가, 그리고 무엇을 수락하는가?*

익명 호출자가 받는 권한을 확인하고, 디바이스 플로로 Keycloak 사용자로 로그인하고, 첫 번째 토큰이 거부되는 이유를
알아낸 다음, 클라이언트를 수정하고, 로그인한 사용자에게 권한 부여가 적용되는 것을 확인합니다.

.OIDC 토큰이 처음이신가요?
[%collapsible]
====
* *JWT* — 서명된 JSON 토큰입니다. 게이트웨이는 서명, 발급자, audience, 만료 시간을 검사합니다.
* *`aud`(audience)* — 토큰의 대상 서비스입니다. 게이트웨이는 ``openshell-gateway``를 요구합니다.
* *`azp`(authorized party)* — 토큰을 요청한 클라이언트이며, audience가 아닙니다.
* *디바이스 플로* — 터미널용 로그인 방식입니다. CLI가 URL과 코드를 표시하면 브라우저에서 승인합니다.
* *프로토콜 매퍼* — 토큰에 클레임(여기서는 audience)을 추가하는 Keycloak 클라이언트 설정입니다.
====

== 기술적 배경

게이트웨이는 OIDC가 활성화된 상태(발급자 `https://keycloak.{cluster_domain}/realms/{keycloak_realm}`,
audience `openshell-gateway`)로 실행되며, 랩을 로그인 없이 시작할 수 있도록 데모 차트가 설정한
``allow_unauthenticated_users = true``도 함께 적용되어 있습니다. ``--oidc-issuer``로 등록된 CLI 게이트웨이는 모든
호출에 베어러 토큰을 보냅니다. 게이트웨이는 Keycloak의 키로 서명을 검사하고, 발급자, audience, 만료 시간을 검사합니다.

== 학습 목표

* 익명 호출자가 어떤 ID와 역할을 받는지 보여 줍니다.
* OIDC 디바이스 플로로 게이트웨이에 로그인하고 검증된 ID를 확인합니다.
* `aud` 클레임이 없는 토큰이 거부되는 이유를 설명하고 클라이언트를 수정합니다.
* 인증(누구인가)과 권한 부여(역할이 무엇을 허용하는가)를 구분합니다.

== 실습 1: 익명 호출자는 무엇을 받는가?

[source,bash,role="execute",subs="attributes+"]
----
openshell whoami
----

예상 결과: `Subject: unauthenticated-local-dev`, `Provider: local_dev`, ``Roles: openshell-user,
openshell-admin``이 표시됩니다. 게이트웨이에 접속할 수 있는 사람은 누구나 관리자입니다. 그래서 모듈 1에서 공개 Route를
제거하고 NetworkPolicy를 추가했습니다. 프로덕션 환경에서는 익명 접근 자체를 제거합니다.

== 실습 2: Keycloak 사용자 생성 및 디바이스 플로 활성화

차트의 클라이언트는 브라우저가 없는 터미널에 필요한 디바이스 그랜트를 허용하지 않습니다. 다음 Keycloak Admin
REST 호출은 임의의 비밀번호로 사용자 ``demo-engineer``를 생성하고(이전의 ``demo-engineer``는 교체되므로 블록을 다시
실행해도 안전합니다) 그랜트를 활성화합니다.

[source,bash,role="execute",subs="attributes+"]
----
KEYCLOAK_URL=https://$(oc get route -n keycloak-system -o jsonpath='{.items[0].spec.host}')
kc_admin() {
  local pw; pw=$(oc get secret keycloak-admin-user -n keycloak-system -o jsonpath='{.data.password}' | base64 -d)
  curl -sk "$KEYCLOAK_URL/realms/master/protocol/openid-connect/token" -d client_id=admin-cli -d username=admin --data-urlencode "password=$pw" -d grant_type=password | jq -r .access_token
}
ADMIN_TOKEN=$(kc_admin)
CLIENT_UUID=$(curl -sk "$KEYCLOAK_URL/admin/realms/{keycloak_realm}/clients?clientId=openshell-gateway" -H "Authorization: Bearer $ADMIN_TOKEN" | jq -r '.[0].id')
OLD_ID=$(curl -sk "$KEYCLOAK_URL/admin/realms/{keycloak_realm}/users?username=demo-engineer&exact=true" -H "Authorization: Bearer $ADMIN_TOKEN" | jq -r '.[0].id // empty')
[ -n "$OLD_ID" ] && curl -sk -o /dev/null -X DELETE "$KEYCLOAK_URL/admin/realms/{keycloak_realm}/users/$OLD_ID" -H "Authorization: Bearer $ADMIN_TOKEN"
DEMO_PW=$(openssl rand -hex 8)
jq -n --arg pw "$DEMO_PW" '{username:"demo-engineer",enabled:true,email:"demo-engineer@example.com",emailVerified:true,firstName:"Demo",lastName:"Engineer",credentials:[{type:"password",value:$pw,temporary:false}]}' \
  | curl -sk -o /dev/null -w "create user: HTTP %\{http_code}\n" -H "Authorization: Bearer $ADMIN_TOKEN" -H "Content-Type: application/json" -d @- "$KEYCLOAK_URL/admin/realms/{keycloak_realm}/users"
curl -sk "$KEYCLOAK_URL/admin/realms/{keycloak_realm}/clients/$CLIENT_UUID" -H "Authorization: Bearer $ADMIN_TOKEN" \
  | jq '.attributes["oauth2.device.authorization.grant.enabled"] = "true"' \
  | curl -sk -o /dev/null -w "enable device grant: HTTP %\{http_code}\n" -X PUT -H "Authorization: Bearer $ADMIN_TOKEN" -H "Content-Type: application/json" -d @- "$KEYCLOAK_URL/admin/realms/{keycloak_realm}/clients/$CLIENT_UUID"
echo "demo-engineer password: $DEMO_PW"
----

예상 결과: `create user: HTTP 201`, ``enable device grant: HTTP 204``가 표시되고, 마지막 줄에
``demo-engineer password: `` 뒤에 16자리 16진수 문자가 표시됩니다(실습 3을 위해 보관하십시오. 이 비밀번호는 여러분의 셸과
Keycloak에만 존재하며, 정리 페이지에서 사용자를 삭제합니다).

== 실습 3: 로그인한 다음 토큰이 거부되는 것을 확인

게이트웨이를 OIDC로 보호되는 게이트웨이로 등록합니다. 등록하면 로그인도 함께 진행됩니다. ``OPENSHELL_NO_BROWSER=1``은 CLI가
디바이스 플로를 사용하도록 합니다. 이 설정이 없으면 CLI는 브라우저가 접근할 수 없는 터미널 파드에서 브라우저 콜백을 기다립니다.

[source,bash,role="execute",subs="attributes+"]
----
export OPENSHELL_NO_BROWSER=1
openshell gateway add "$OPENSHELL_GATEWAY_ENDPOINT" --name ztm-demo \
  --oidc-issuer "$KEYCLOAK_URL/realms/{keycloak_realm}" \
  --oidc-client-id openshell-gateway --oidc-audience openshell-gateway --gateway-insecure < /dev/null
----

CLI는 ``✓ Gateway 'ztm-demo' added``를 출력한 다음, ``To authenticate, visit:``과 ``user_code=…``로 끝나는 URL을 출력하고 대기합니다.

. 새 브라우저 탭에서 URL을 엽니다.
. 실습 2에서 출력된 비밀번호로 ``demo-engineer``로 로그인합니다(화면에서 지나갔다면 ``echo $DEMO_PW``를 실행하십시오).
. *Grant Access to OpenShell Gateway*(OpenShell Gateway에 대한 접근 권한 부여)에서 *Yes*(예)를 클릭합니다.

예상 결과: 브라우저에 *Device Login Successful*(디바이스 로그인 성공)이 표시되고 터미널에 ``✓ Authenticated via device code``가 출력됩니다.
Keycloak이 토큰을 발급했습니다. 이제 토큰을 사용합니다.

[source,bash,role="execute",subs="attributes+"]
----
openshell -g ztm-demo whoami
----

예상 결과: ``invalid token: Missing required claim: aud``와 함께 ``whoami requires authentication``이 표시됩니다. 게이트웨이가
Keycloak이 발급한 토큰을 거부했습니다.

== 실습 4: audience를 추가하고 다시 로그인

Keycloak은 요청한 클라이언트를 ``aud``가 아니라 ``azp``에 넣습니다. audience 매퍼가 ``aud``에 ``openshell-gateway``를 추가합니다.
그런 다음 다시 로그인하고, 이전처럼 브라우저에서 새 코드를 승인합니다(비밀번호를 입력하지 않아도 될 수 있습니다).

[source,bash,role="execute",subs="attributes+"]
----
ADMIN_TOKEN=$(kc_admin)
curl -sk -o /dev/null -w "audience mapper: HTTP %\{http_code}\n" -H "Authorization: Bearer $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{"name":"openshell-gateway-audience","protocol":"openid-connect","protocolMapper":"oidc-audience-mapper","config":{"included.client.audience":"openshell-gateway","access.token.claim":"true","id.token.claim":"false"}}' \
  "$KEYCLOAK_URL/admin/realms/{keycloak_realm}/clients/$CLIENT_UUID/protocol-mappers/models"
openshell gateway login ztm-demo
----

예상 결과: ``audience mapper: HTTP 201``과 새 `user_code` URL이 표시되고, 승인하면
``✓ Authenticated to gateway 'ztm-demo' as demo-engineer``가 표시됩니다.

게이트웨이가 검증한 ID를 확인합니다.

[source,bash,role="execute",subs="attributes+"]
----
openshell -g ztm-demo whoami
----

예상 결과: `Name: demo-engineer`, `Provider: oidc`, 그리고 비어 있는 ``Roles``가 표시됩니다. 게이트웨이가 토큰의
서명, 발급자, audience를 검사하고 토큰에서 ID를 가져왔습니다.

== 실습 5: 인증되었다고 권한이 부여된 것은 아님

[source,bash,role="execute",subs="attributes+"]
----
openshell -g ztm-demo sandbox list; echo "exit=$?"
----

예상 결과: ``role 'openshell-user' required``와 ``exit=1``이 표시됩니다. 게이트웨이는 ``demo-engineer``가 누구인지 알고 있지만,
이 사용자는 OpenShell 역할을 가지고 있지 않으므로 거부됩니다. 반면 익명 호출자는 관리자입니다. 프로덕션 환경에서는
``allowUnauthenticatedUsers: false``로 설정하고 `rolesClaim`, `userRole`, ``adminRole``로 Keycloak 역할을 매핑합니다.

마지막으로, 다음 모듈에서 다시 랩의 익명 접근을 사용하도록 OIDC 등록을 제거합니다.

[source,bash,role="execute",subs="attributes+"]
----
openshell gateway remove ztm-demo
openshell sandbox list
----

예상 결과: ``Gateway registration 'ztm-demo' removed.``가 표시된 다음, 모듈 2에서처럼 ``{sandbox_name}``이 ``Ready``로 표시됩니다.

IMPORTANT: ``ztm-demo``가 등록되어 있는 동안에는 `OPENSHELL_GATEWAY_ENDPOINT` 변수를 사용하더라도 CLI가 게이트웨이에
OIDC를 적용하므로, 모듈 9가 ``OIDC credentials are missing``으로 실패합니다.

== 증거 확인

* 게이트웨이가 검사한 토큰 클레임 중 Keycloak이 기본적으로 설정하지 않은 것은 무엇입니까?
* 이 랩에서 OIDC가 활성화된 게이트웨이가 여전히 열려 있는 이유는 무엇입니까?

.정답
[%collapsible]
====
* ``aud``입니다. Keycloak은 클라이언트를 ``azp``에 지정했고, 게이트웨이는 ``aud``에 ``openshell-gateway``가 있어야 하므로
  audience 매퍼가 이를 추가할 때까지 토큰을 거부했습니다.
* ``allow_unauthenticated_users = true``는 토큰이 없는 호출자에게 관리자 역할을 가진 `local_dev` ID를 부여합니다.
  OIDC는 그 위에 검증된 ID를 추가할 뿐이며, 익명 경로를 제거하지는 않습니다.
====
